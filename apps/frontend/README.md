# Hy-Nomas Frontend

[Chinese version](README_CN.md)

This directory contains the React + TypeScript web frontend for Hy-Nomas.

The page currently calls a synchronous HTTP endpoint:

```text
POST /v1/generate
```

The backend is provided by `apps/seg_ar_web_server.py`. Its `--rollout-type` option supports:

- `seg_ar`: loads and keeps `CPTCausalInferencePipeline` resident. Model text comes from the prompt submitted by the page.
- `oneshot`: loads and keeps `MultiPromptBidirectionalPipeline` resident. The page's `subject` field must contain the absolute path to a `.txt` file accessible to the server. The backend reads model text from this file rather than using the JSON/text prompt generated by the page.

After submitting a request, the page waits for generation to finish and plays the MP4 using the `video_url` returned by the backend.

## Feature Scope

The page currently supports:

- Selecting a perspective and visual style
- Entering world subject and environment descriptions
- Entering subsequent actions or scene instructions
- Generating video through the `seg_ar` backend
- Displaying generation, completion, and failure states
- Playing the video returned by the backend

The current implementation performs synchronous, one-off video generation:

```text
Submit prompt
  -> Wait for GPU inference
  -> Backend encodes MP4
  -> Return video_url
  -> Browser plays the video
```

It is not yet a real-time interaction loop that continuously retains world state and KV cache. Each page request runs an independent `seg_ar` inference.

## Deploying the Frontend and Backend

Download the weights following [Model Assets](../../README.md#model-assets) and set `Hy_Nomas_Model_Path` to the download directory; the launch commands below reuse its value.

Deploying the frontend and backend on the same GPU machine is recommended:

```text
Browser
   |
   | HTTP
   v
seg_ar_web_server.py:8082
   |
   +-- /                 apps/frontend/dist static frontend
   +-- /v1/generate      seg_ar inference API
   +-- /outputs/         Generated videos
   +-- /health           Health check
```

`seg_ar_web_server.py` already serves static frontend files. When connecting the model, **you do not need and must not run `python -m http.server` on port 8082 at the same time**.

### Separate Gateway and GPU Worker

Use the following entry point to start the demo Gateway and GPU workers:

```bash
bash scripts/inference/start_seg_ar_demo.sh
```

Configure your model files in `configs/experiment/inference.yaml` before starting,
or override them with startup arguments. See the [demo deployment guide](../README.md).
Benchmark prompts are only required for the optional dry-run, not for normal online generation.

- `apps/seg_ar_gateway.py`: listens on port 8081 by default, configurable with `PORT`, and serves the frontend, API, output files, and persistent task queue.
- `apps/seg_ar_web_server.py --worker-only`: keeps the GPU model resident and claims tasks from the queue. GPU count is determined by `parallelism.sp_size` and the startup topology.
- The queue defaults to `/tmp/nomas_seg_ar_jobs.json`. The Gateway stays online when GPU workers restart, and unfinished tasks are requeued.
- Each GPU worker slot uses a file lock to prevent duplicate launches.

### Optional Dry Run

Specify benchmark prompts through the same demo entry point to enable the **Dry run** button:

```bash
bash scripts/inference/start_seg_ar_demo.sh \
  inference.prompt=/path/to/benchmark.json
```

You can also set `inference.prompt` in `configs/experiment/inference.yaml`,
pass `--dry-run-source /path/to/benchmark.json`, or use the `DRY_RUN_SOURCE`
environment variable. The worker randomly selects a sample from this file
and updates the video and captions as segments finish. No separate HTTP inference
service is required.

### Natural-Language Action PE

Normal user input is no longer concatenated directly into a natural-language DiT prompt.
The Gateway uses the selected PE model's API to convert the perspective choice in Setup,
`Subject Description`, and `Environment Description` into JSON matching the
training format:
`perspective_view + Style + subject_list + segments + contained_actions`.
It then submits this JSON to the GPU worker. K3 refines the user's `first-person`
selection into `first-person` or `second-person`, and `third-person` into
`third-person follow` or `third-person observer`, and infers Style from the two
descriptions. Every K3 request after the first turn samples up to 40 frames
from the immediately preceding segment at approximately 2 FPS as visual continuity
conditioning. Frames retain their original aspect ratio, with the short side
downsampled to 480 pixels; frames whose short side is already at most 480 pixels
are not upscaled. The complete multimodal user message is saved in the session's
conversation history, so later requests replay the accumulated segment video
frames and turn prompts, not just text JSON. Requests follow the large-scale
captioning pipeline's multi-image protocol: the current user instruction comes
first, followed by each image's absolute `video_timestamp` and
`segment_relative_time` text, then the image itself. K3 uses high thinking
for the current turn. Historical assistant turns retain only the final JSON,
not thinking blocks.
Camera-control turns send the trajectory JSON cleaned for PE to K3 as the
`camera_control` value, including all pose frames, timestamps, position,
quaternion/Euler, duration, coordinate/scale metadata, and keyEvents.
DiT still uses the original trajectory; the `<camera-control-stream>` placeholder
is no longer used.

The Gateway uses an existing SGLang OpenAI-compatible endpoint:

```bash
export PE_API_URL=http://localhost:30000/v1/chat/completions
export PE_MODEL=Nomas-PE
# Optional, only if the endpoint requires a bearer token:
export PE_API_KEY=...
```

Without `PE_API_KEY`, it sends no Authorization header. `PE_MODEL` is the
preferred default model id served by SGLang. The Gateway queries `/v1/models`
at the same API address and exposes the advertised models in the Setup and
Studio **Prompt enhancer** selectors, even when there is only one model.
If the preferred default is not advertised, the first advertised model becomes
the default. Thinking mode and LLM random seed remain configurable for each
request. Failed requests never switch to another model. Model lists are cached
for 60 seconds; failed discovery is retried after 5 seconds.
The API address can also be a base URL or a `/v1` URL.
`PE_API_TIMEOUT` and `PE_API_RETRIES` optionally
override the request timeout (300 seconds) and retry count (3).

By default, it uses the system, first-turn, and intermediate-turn Markdown prompts
under `apps/prompts/`, and retains every turn's complete multimodal user message
in subsequent conversation history.

Start the SGLang service separately. The demo does not write credentials to the
queue, logs, or Git.

Stop both processes:

```bash
bash scripts/inference/stop_seg_ar_demo.sh
```

### oneshot File Prompt Mode

#### Mode Overview

`oneshot` is the rollout name exposed by the Web Server. Internally, it uses:

```text
MultiPromptBidirectionalPipeline
```

It maps to the following name in the existing inference configuration:

```text
one_shot
```

The two Web rollout modes use different prompt sources:

| Web Rollout | Pipeline | Model Text Source |
| --- | --- | --- |
| `seg_ar` | `CPTCausalInferencePipeline` | The page request's `prompt` |
| `oneshot` | `MultiPromptBidirectionalPipeline` | The `.txt` file referenced by the page's `subject` |

A service process loads only one pipeline. To switch modes, shut down the service
correctly and restart it with a different `--rollout-type`.

#### Start the oneshot Service

Example with 8 GPUs:

```bash
export Hy_Nomas_Model_Path="${Hy_Nomas_Model_Path:-/path/to/Hy-Nomas}"

torchrun \
  --standalone \
  --nproc_per_node=8 \
  apps/seg_ar_web_server.py \
  +experiment=inference \
  --rollout-type oneshot \
  --dit-weight "${Hy_Nomas_Model_Path}/DiT/distilled/diffusion_pytorch_model_ema_0_995.safetensors" \
  model.vae.checkpoint="${Hy_Nomas_Model_Path}/VAE/PixelUMM_FT/diffusion_pytorch_model.safetensors" \
  inference.video_fps=24 \
  --host 0.0.0.0 \
  --port 8082
```

`oneshot` does not require fixing the following at startup:

```text
inference.num_frames
```

When the request does not explicitly provide `num_frames`, the backend reads
timestamps from the prompt file and derives the total frame count using
`inference.video_fps=24`.

#### Page Workflow

1. Select first-person or third-person on the Setup page. The `oneshot` backend
   does not use this option to construct the page prompt, but the frontend still
   displays it.
2. Enter the absolute path to a `.txt` file accessible to the backend server in
   the `Prompt file` field, for example:

   ```text
   /path/to/prompt.txt
   ```

3. Click `Enter world` to open Studio.
4. `Enter world` currently only changes pages; it does not start generation.
5. Enter any nonempty text in the right-hand `What should happen next?` field,
   for example:

   ```text
   Generate this video
   ```

6. Press Enter or click the send button to call:

   ```text
   POST /v1/generate
   ```

The page request resembles:

```json
{
  "prompt": "Text constructed by the page; the oneshot backend does not use it",
  "subject": "/path/to/prompt.txt"
}
```

The current frontend does not send `num_frames`. This is the request format needed
for oneshot's automatic-duration mode.

#### Prompt File Requirements

The backend validates `subject` as follows:

- It must be an absolute path starting with `/`.
- It must be accessible to the server or container running the backend.
- The file must exist and end in `.txt`.
- The file must use UTF-8.
- The file must not be empty.
- The file must not exceed 2 MiB.

Do not add quotes or explanatory text to Prompt file:

```text
# Correct
/path/to/prompt.txt

# Incorrect
"/path/to/prompt.txt"

# Incorrect
Prompt file: /path/to/prompt.txt
```

The file can contain one JSON prompt or several JSON prompts separated by `|||`:

```text
{"segments": [...]}|||{"segments": [...]}|||{"segments": [...]}
```

After reading the file, the backend runs:

```python
prompts = [
    part.strip()
    for part in file_content.split("|||")
    if part.strip()
]
```

The file is read on rank 0, which then broadcasts the parsed prompts and inference
parameters to the other sequence-parallel ranks.

#### Automatic Frame Count

A fixed 24 FPS only converts duration into frame count. Video duration still comes
from timestamps in the prompt file.

For each `|||` prompt, the backend looks for timestamps in this order:

1. `segments[*].contained_actions[*].start_time/end_time`
2. `segments[*].start_time/end_time`

Each segment's duration is:

```text
segment_duration =
    maximum end_time in the segment - minimum start_time in the segment
```

The durations are accumulated at the configured FPS:

```text
boundary_i = int(cumulative duration × FPS)
num_frames = final boundary
```

For example, a sample file contains three segments:

```text
15.00 seconds
15.00 seconds
13.88 seconds
```

At 24 FPS, this produces:

```text
pixel-frame boundaries = [0, 360, 720, 1053]
num_frames = 1053
Total playback duration = 1053 / 24 = 43.875 seconds
```

The backend passes these pixel-frame boundaries to `MultiPromptBidirectionalPipeline`.
The pipeline then converts them into internal temporal-token boundaries using the
VAE temporal ratio and the model's temporal patch size.

If the request explicitly includes:

```json
{
  "num_frames": 361
}
```

The explicit value takes priority, and total frame count is no longer inferred
from prompt timestamps. Normal page usage does not need this field.

If a prompt is not valid JSON, or a segment has no usable `end_time`, the backend
returns HTTP 400. Fix the prompt file or explicitly provide `num_frames` through
the API.

#### Check the Service Configuration

```bash
curl http://127.0.0.1:8082/v1/config
```

Expected response in oneshot mode:

```json
{
  "rollout_type": "oneshot",
  "prompt_source": "subject_file",
  "num_frames": null,
  "num_frames_source": "prompt_timestamps",
  "fps": 24

```

If it returns:

```json

  "rollout_type": "seg_ar"
}
```

and restart it.

#### Common Errors

`oneshot subject path must be absolute`

: Subject is not an absolute path starting with `/`, or the path contains quotes
  or explanatory text.

`oneshot prompt file does not exist`

: The file is not accessible in the backend container, or the path is misspelled.

`oneshot automatic frame selection requires every '|||' prompt to be JSON`

: The request did not provide `num_frames`, but a prompt in the file is not valid JSON.

`has no usable end_time`

: A prompt has no action or segment end time, so its duration cannot be inferred.

`oneshot has ... temporal tokens; increase num_frames`

: The explicitly supplied `num_frames` is too short to allocate valid temporal
  tokens to every prompt segment.

The model ID or local directory is configured independently of the encoder type:


```bash

  --nproc_per_node=8 \
  apps/seg_ar_web_server.py \
```

```bash
  --dit-weight "${Hy_Nomas_Model_Path}/DiT/distilled/diffusion_pytorch_model_ema_0_995.safetensors" \
  model.vae.checkpoint="${Hy_Nomas_Model_Path}/VAE/PixelUMM_FT/diffusion_pytorch_model.safetensors" \
  --host 0.0.0.0 \
  --port 8082
```

The service starts exactly one complete sequence-parallel model replica, so:

```text
WORLD_SIZE == parallelism.sp_size
```

Rank 0 is responsible for:

- Starting FastAPI/uvicorn
- Receiving page requests
- Broadcasting requests to other ranks
- Encoding and returning video

Nonzero ranks enter a resident worker loop and wait for rank 0 to broadcast each request.

## Shutting Down the Service Correctly

In multi-GPU mode, do not stop only rank 0 or kill an individual worker rank.
Nonzero ranks are waiting for distributed broadcasts from rank 0. Killing only
one process can leave other ranks blocked in an NCCL collective or broadcast.

The correct shutdown sequence is:

```text
Stop accepting new requests
  -> Wait for the current generation request to finish
  -> Rank 0 broadcasts SHUTDOWN
  -> Nonzero ranks exit their worker loops
  -> All ranks release the pipeline and CUDA cache
  -> Destroy the distributed process group
  -> torchrun exits
```

### Stop a Foreground Service

If the service runs directly in the current terminal, use:

```text
Ctrl+C
```

Press it once and wait for:

```text
Graceful shutdown requested
Shutdown command delivered to worker ranks
[rank N] shutdown received
[rank N] model resources released
```

Do not repeatedly press `Ctrl+C` during normal shutdown. Otherwise, torchrun may
terminate workers before graceful cleanup finishes.

### Stop Through the HTTP API

To stop the service from another terminal or an administration page, set a shutdown
token before startup:

```bash
export NOMAS_SHUTDOWN_TOKEN="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
echo "$NOMAS_SHUTDOWN_TOKEN"
```

Start the service normally. `seg_ar_web_server.py` reads the token from the environment:

```bash
export Hy_Nomas_Model_Path="${Hy_Nomas_Model_Path:-/path/to/Hy-Nomas}"

torchrun \
  --standalone \
  --nproc_per_node=8 \
  apps/seg_ar_web_server.py \
  +experiment=inference \
  --dit-weight "${Hy_Nomas_Model_Path}/DiT/distilled/diffusion_pytorch_model_ema_0_995.safetensors" \
  model.vae.checkpoint="${Hy_Nomas_Model_Path}/VAE/PixelUMM_FT/diffusion_pytorch_model.safetensors" \
  --host 0.0.0.0 \
  --port 8082
```

Request shutdown locally on the server:

```bash
curl -X POST \
  -H "Authorization: Bearer ${NOMAS_SHUTDOWN_TOKEN}" \
  http://127.0.0.1:8082/v1/shutdown
```

Response:

```json
{
  "status": "stopping"
}
```

To keep the token out of shell history and process listings, use the
`NOMAS_SHUTDOWN_TOKEN` environment variable instead of passing:

```bash
--shutdown-token <plaintext-token>
```

If neither `NOMAS_SHUTDOWN_TOKEN` nor `--shutdown-token` is set, `POST /v1/shutdown`
is disabled and returns HTTP 404.

After receiving the shutdown request, the service first returns HTTP 202 and then
enters uvicorn lifespan shutdown. If generation is in progress, it waits for the
request to finish before broadcasting `SHUTDOWN`; it does not release the model
in the middle of a DiT/NCCL collective.

### Force Shutdown in Exceptional Cases

Only if graceful shutdown remains unresponsive for a long time should you terminate
the outermost `torchrun` process rather than killing ranks individually:

```bash
ps -ef | grep '[t]orchrun.*seg_ar_web_server.py'
kill -TERM <torchrun-pid>
```

Wait, then check:

```bash
ps -ef | grep '[s]eg_ar_web_server.py'
```

Use the following only as a last resort:

```bash
kill -KILL <torchrun-pid>
```

Forced shutdown may skip CUDA, NCCL, and output-file cleanup. It should not be the
normal way to stop the service.

### Multi-Segment seg_ar

The frontend supports pasting structured JSON directly. Put JSON in
`Subject Description` on the Setup page and any nonempty text in
`Environment Description` before entering Studio. Alternatively, paste JSON
directly into Studio's direction input.

Example JSON:

```json
{
  "perspective_view": "first-person",
  "segments": [
    {
      "visual_description_long": "A fox stands in a forest.",
      "contained_actions": [
        {
          "start_time": "00:00.000",
          "end_time": "00:02.000",
          "action_description": "The fox looks toward the river."
        }
      ]
    },
    {
      "description_change": "The fox begins walking.",
      "contained_actions": [
        {
          "start_time": "00:00.000",
          "end_time": "00:01.500",
          "action_description": "The fox walks forward."
        }
      ]
    }
  ]
}
```

The frontend reads `fps` from `/v1/config`, serializes each `segments[i]` as a
separate prompt, and joins them with `|||`. Each segment's duration is computed
from action/segment timestamps, then accumulated to generate pixel-frame boundaries.

At 24 FPS, the JSON above produces this request:

```json
{
  "prompt": "{\"perspective_view\":\"first-person\",\"segments\":[...]}|||{\"segments\":[...]}",
  "num_frames": 84,
  "segment_boundaries": [0, 48, 84]
}
```

Calculation:

```text
segment 0: 2.0 seconds × 24 FPS = 48 frames
segment 1: 1.5 seconds × 24 FPS = 36 frames
boundaries: [0, 48, 84]
num_frames: 84
```

The backend does not trust the frontend's results. It reparses the JSON and
timestamps of each `|||` prompt and validates:

```text
Number of segment_boundaries = number of prompt segments + 1
segment_boundaries[0] = 0
Final boundary = num_frames
All boundaries are strictly increasing
Frontend boundaries = boundaries recomputed from prompt timestamps and FPS
Frontend num_frames = total frame count recomputed by the backend
```

Inconsistent values return HTTP 400. For ordinary natural-language prompts without
`segments` JSON, frontend automatic calculation is not enabled, and the backend's
configured `inference.num_frames` is used.
